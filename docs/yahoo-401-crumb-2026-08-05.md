## PARTE A — Diagnóstico de la autenticación

### A.1 — `getYahooAuth` completo, cómo obtiene crumb/cookie, caché y manejo de fallos

Cita literal, `lib/yahoo.js:275-293`:

```js
async function getYahooAuth() {
  if (yahooAuthCache?.crumb && yahooAuthCache.expiresAt > Date.now()) return yahooAuthCache;
  const seedUrls = ["https://fc.yahoo.com", "https://finance.yahoo.com", "https://www.yahoo.com"];
  let cookie = "";
  for (const seedUrl of seedUrls) {
    const seed = await fetch(seedUrl, { headers: { "User-Agent": "Mozilla/5.0", Accept: "text/html,*/*" }, cache: "no-store", redirect: "manual" }).catch(() => null);
    cookie = seed?.headers ? cookieHeaderFrom(seed.headers) : "";
    if (cookie) break;
  }
  const crumbRes = await fetch("https://query1.finance.yahoo.com/v1/test/getcrumb", {
    headers: { "User-Agent": "Mozilla/5.0", Accept: "text/plain,*/*", ...(cookie ? { Cookie: cookie } : {}) },
    cache: "no-store",
  });
  if (!crumbRes.ok) throw new Error(`Yahoo ownership auth HTTP ${crumbRes.status}`);
  const crumb = (await crumbRes.text()).trim();
  if (!crumb || crumb.includes("<")) throw new Error("Yahoo ownership auth no valido");
  yahooAuthCache = { crumb, cookie, expiresAt: Date.now() + 60 * 60 * 1000 };
  return yahooAuthCache;
}
```

Mecanismo: 1) recorre `seedUrls` (`fc.yahoo.com`, `finance.yahoo.com`, `www.yahoo.com`) hasta obtener una cookie de `Set-Cookie` (usa la primera que no esté vacía; `redirect: "manual"`, no sigue redirecciones); 2) pide un crumb a `query1.finance.yahoo.com/v1/test/getcrumb` con esa cookie; 3) si la respuesta no es `ok` o el cuerpo está vacío o contiene `<` (HTML de error), lanza. Si todo sale bien, cachea `{crumb, cookie, expiresAt}` en el módulo-global `yahooAuthCache` (línea 12) durante **1 hora** (`Date.now() + 60 * 60 * 1000`).

### A.2 — ¿Reintenta en 401? ¿Invalida el caché o lo reutiliza?

No reintenta dentro de la misma llamada. La invalidación ocurre en el **consumidor** (`fetchYahooQuoteSummary`), no en `getYahooAuth`. Cita, `lib/yahoo.js:310-320`:

```js
  const auth = await getYahooAuth();
  const params = new URLSearchParams({ modules, crumb: auth.crumb });
  const url = `https://query2.finance.yahoo.com/v10/finance/quoteSummary/${encodeURIComponent(yahooSymbol)}?${params.toString()}`;
  const res = await fetch(url, {
    headers: { ...YAHOO_HEADERS, ...(auth.cookie ? { Cookie: auth.cookie } : {}) },
    next: { revalidate: 86400 },
  });
  if (!res.ok) {
    if (res.status === 401 || res.status === 403) yahooAuthCache = null;
    throw new Error(`Yahoo profile HTTP ${res.status}`);
  }
```

Si la respuesta es 401/403, pone `yahooAuthCache = null` y **lanza** — la llamada en curso falla, no reintenta con un crumb nuevo dentro de la misma invocación. La invalidación solo sirve para forzar que la **siguiente** llamada (a `fetchYahooQuoteSummary`, en el próximo símbolo o en el próximo scan) vuelva a ejecutar el flujo completo de `getYahooAuth`. En el rango de tiempo entre invalidación y esa siguiente llamada, cualquier otro consumidor que ya tuviera `auth` en una variable local (no releído) seguiría usando el crumb viejo hasta que a su vez reciba un 401/403.

Nota: si el 401 fuera devuelto directamente por `query1.finance.yahoo.com/v1/test/getcrumb` (es decir, si el fallo estuviera en la obtención del crumb, no en su uso), `getYahooAuth` lanzaría en la línea 288 (`if (!crumbRes.ok) throw ...`) y **nunca llegaría a cachear nada** — no hay caso especial para eso, es el mismo `throw` genérico.

## PARTE C — Efecto en los scores

### C.8 — Camino de `growthScore`/`epsGrowthProxyScore`/composite cuando el bloque fundamental está ausente

**`growthScore`**, `lib/scoringEngine.js:494-502`:
```js
    compute: (r) => {
      const metrics = r.growthMetrics || {};
      const values = ["revenueGrowth", "earningsGrowth", "grossMargin", "operatingMargin", "profitMargin", "roe", "roa", "debtToEquity", "currentRatio"].map((k) => metrics[k]);
      // Sin ningún campo finito no hay señal de crecimiento que calcular — se
      // señaliza ausencia (null), igual que epsGrowthProxyScore (línea 547), en
      // vez de fabricar un 45 "neutro" indistinguible de una medición real.
      if (!values.some(Number.isFinite)) return null;
```

**`epsGrowthProxyScore`**, `lib/scoringEngine.js:546-556`:
```js
    compute: (r) => {
      const metrics = r.growthMetrics || {};
      const revenue = metrics.revenueGrowth;
      const earnings = metrics.earningsGrowth;
      ...
      if (![revenue, earnings, operating, profit, roe, roa].some(Number.isFinite)) return null;
```

Con `growthMetrics = {}` (fundamentales completamente ausentes), ambas funciones devuelven **`null` explícitamente por diseño** — no `0`, no excepción, no valor "neutro" fabricado. `fundamentalCoverageScore` (`lib/researchRow.js`, vía `coveragePct` sobre 13 campos de `growthMetrics`) sería `0` en ese mismo escenario.

Cómo llega `growthMetrics = {}` a una fila: `lib/serverScanRunner.js:216-226`:
```js
        try {
          const [chart, profile] = await Promise.all([
            fetchYahooChart(symbol),
            fetchYahooProfile(symbol).catch(() => ({})),
          ]);
          state.buffer.push(buildResearchRow(symbol, chart, profile, rowOptions, benchmarks));
        } catch (error) {
          const classified = classifyProviderError(error);
          state.kindBreakdown[classified.kind] = (state.kindBreakdown[classified.kind] || 0) + 1;
          state.errors.push({ symbol, reason: classified.reason, kind: classified.kind, status: classified.status });
        }
```
`.catch(() => ({}))` en la línea de `fetchYahooProfile` traga cualquier rechazo (incluido un fallo de `getYahooAuth`/crumb) y entrega `profile = {}`. La fila se construye igual, con `chart` (precio/histórico, vía `fetchYahooChartDirect`, que **no** requiere crumb — confirmado leyendo `lib/yahoo.js:1226-1281`, ningún llamado a `getYahooAuth` en su cuerpo) pero `profile.growthMetrics` queda `undefined` → en `lib/researchRow.js:237` (`growthMetrics: profile.growthMetrics || {}`) queda `{}`. Este fallo **nunca llega a `state.errors`** porque el `.catch` intercepta antes del `try/catch` externo — el contador `errors` del progreso del scan solo refleja fallos de `fetchYahooChart` o excepciones de `buildResearchRow`, no la ausencia silenciosa de fundamentales. Esto confirma textualmente la premisa del enunciado sobre el mecanismo del fallo, independientemente de que no se haya podido reproducir el 401 en sí (Parte A.3).

Nota adicional: `fetchYahooProfile` (`lib/yahoo.js:1311-1378`) ya tiene su propia capa de tolerancia con `Promise.allSettled` sobre sus 4 sub-fuentes (`quoteSummary`, `fetchYahooFundamentals`, `fetchYahooSearchProfile`, `fetchYahooQuote`) y **nunca lanza** — siempre resuelve un objeto, con `profileProviderError` listando los mensajes de las sub-fuentes que fallaron. Es decir, el `.catch(() => ({}))` de `serverScanRunner.js` normalmente no se activa por un fallo aislado de `quoteSummary`: `fetchYahooProfile` ya absorbe eso internamente y devuelve un perfil parcial (con `growthMetrics` derivado de lo que sí respondió, p. ej. `fetchYahooFundamentals`, que **tampoco** requiere crumb — usa `ws/fundamentals-timeseries`, un endpoint distinto sin auth, confirmado en `lib/yahoo.js:1066-1109`). El `.catch` externo solo entraría en juego si las 4 sub-fuentes fallaran simultáneamente Y algo dentro de `fetchYahooProfile` mismo lanzara antes del `Promise.allSettled` (no identificado ningún punto así en el cuerpo de la función) — o si `fetchYahooProfile` recibiera una señal de aborto externa (timeout del `Promise.all` en `serverScanRunner.js` junto a `fetchYahooChart`). **Esto explica por parte la Parte B.5**: incluso si `quoteSummary` falla, `growthScore`/`epsGrowthProxyScore` pueden seguir teniendo valor porque su fuente primaria efectiva (`growthFromQuoteSummary` combinado con `fetchYahooFundamentals` vía `mergeGrowthMetrics`, que prefiere el dato de quoteSummary pero cae a fundamentals-timeseries) no depende exclusivamente del crumb.

## PARTE D — Opciones (sin implementar, sin recomendar)

### D.11 — Opciones para el 401

1. **Reintento con crumb nuevo dentro de la misma llamada**: si `fetchYahooQuoteSummary` recibe 401/403, en vez de solo invalidar el caché y lanzar, podría invocar `getYahooAuth()` de nuevo (forzando refetch) y reintentar una vez antes de propagar el error.
2. **Cambio de endpoint/mecanismo de auth**: usar un flujo de auth distinto si Yahoo lo requiere (a determinar, ver A.4 sin cerrar), o evaluar si algún módulo de `quoteSummary` puede obtenerse sin crumb.
3. **Otro proveedor** para el bloque que depende de `quoteSummary` (ownership, `defaultKeyStatistics`, `financialData`, `summaryDetail`) — nota: `fetchYahooFundamentals` (revenue/márgenes) y `fetchYahooChartDirect` (precio/histórico) ya son independientes del crumb, así que el proveedor alternativo solo tendría que cubrir el subconjunto que sí depende de él.
4. **Marcar la fila como incompleta y no publicarla** cuando `fundamentalCoverageScore` cae debajo de un umbral, en vez de dejar que pase a scoring/composite con constantes fabricadas.

### D.12 — ¿Debería publicarse una fila sin fundamentales?

Hoy: se publica, y si además finaliza (percentiles), sus scores dependientes se completan con las constantes de C.9 sin distinguirse de una fila con datos reales. Alternativas, sin recomendar ninguna:

- **Publicar igual, pero marcar visiblemente la fila como "fundamentales no disponibles"** en la UI (usando `fundamentalCoverageScore`/`profileProviderError`, ya existentes en el dato) para que el usuario decida si confía en el score.
- **Excluir la fila del ranking/composite** (no de la base de datos) cuando la cobertura fundamental está por debajo de un umbral — mantiene el dato crudo pero no lo compara contra filas completas.
- **No persistir la fila en absoluto** hasta que los fundamentales estén disponibles — más estricto, puede reducir la cobertura total de símbolos escaneados si el fallo es frecuente.
- **Mantener el estado actual** (publicar y rellenar con constantes) — es la situación de hoy, con el riesgo ya documentado en C.9/C.10 de que el composite de una fila así no sea comparable al de una fila con datos reales, aunque en la muestra disponible no se detectó ningún caso real de esto ocurriendo.

## CONFIANZA

**Verificado leyendo código** (alta confianza, cita literal disponible):
- `getYahooAuth` completo (`lib/yahoo.js:275-293`) y su caché de 1h.
- La invalidación de caché ocurre en el consumidor (`fetchYahooQuoteSummary`, líneas 317-320), no reintenta en la misma llamada.
- `fetchYahooChartDirect` (`lib/yahoo.js:1226-1281`) no llama a `getYahooAuth` en ningún punto — es independiente del crumb.
- `fetchYahooFundamentals` (`lib/yahoo.js:1066-1109`, endpoint `ws/fundamentals-timeseries`) tampoco requiere crumb.
